# RES-01 — repeated-call memory attribution

Reviewed 2026-10-26 under [#100](https://github.com/BK-Teisrud/SwiftNetworkKit/issues/100). Product baseline: accepted I20 merge `98f23d32834ec5991ba0446cfd36c9966625fa3f`, main run 40408266400. No production Swift source, public API, timeout default or clock/lifecycle semantics are changed by this investigation. Candidate PR/main checks are required before #100 completion.

## Finding and disposition

The I20 RSS rise is corroborated, but a retained NetworkKit response/operation graph was not established. Native heap inspection and a separate network-free control instead identify time-limited Swift sleep-helper/dispatch allocation retention on the observed macOS runtime. Thousands of cancelled, already joined sleeps retain helper allocations until their original deadlines have passed. The live allocations then fall substantially, even though process RSS need not return to its startup value. This attributes the large transient live-allocation component on this host; remaining resident-page ownership is not exhaustively attributed. It is not universal leak-free certification or a claim about every supported OS.

Keep the existing monotonic deadline and joined-cancellation implementation. Replacing ContinuousClock.sleep with Task.sleep(nanoseconds:) does not fix the observed retention: both minimal controls reproduce it. A custom timer/scheduler, polling watchdog or altered clock would add synchronization, wakeup and deadline-semantics risks without a justified v1 contract change. No product ownership defect requiring a small fix was established. The improvement is a repeatable attribution control and a post-budget measurement, preserving the original adverse evidence rather than hiding it with a memory threshold.

Apple's [sleep cancellation documentation](https://developer.apple.com/documentation/swift/task/sleep(until:tolerance:clock:)) describes CancellationError. The allocation-lifetime conclusion here comes from local measurements, not an inferred promise of immediate runtime deallocation. Compiler identity and OS runtime identity are distinct; these results are for macOS 15.8.1 / 24H32 x86_64 with Xcode 26.3 / Swift 6.2.4, not all systems running that compiler.

## Evidence chain

1. [I20 raw baseline](evidence/I20_RESOURCE_BASELINE.json): three repetitions per case, including 6,400 workload calls at concurrency 32. The original short-quiescence RSS rise remains unchanged in the record.
2. [Native heap summary](evidence/RES01_NATIVE_HEAP_SUMMARY.json): the release consumer uses the unchanged public typed/raw NetworkKit pipeline, synthetic local HTTP and a ten-second total budget. A temporary probe-only marker/25-second wait enables heap snapshots after shutdown and after a further eleven seconds. MallocStackLogging and profiler overhead make these allocation observations, not latency/RSS baseline comparisons. One profiled native repetition per mode is retained as sanitized counts; raw address/stack graphs stay local.
3. An allocation tree from the synthetic process's memory graph shows Task._sleep → dispatch_after_f → dispatch_source_create. The immediately sampled native heap contains 3,975 Task-stack nodes and 2,948,016 live malloc bytes. After original deadlines, it contains seven Task-stack nodes and 499,504 live malloc bytes. A separate direct URLSession repetition contains six Task-stack nodes and 527,360 live malloc bytes. No corresponding thousands of named NetworkOperation, NetworkTaskDelegate or DiagnosticObservation instances appear in those type summaries; type-summary absence alone is not a complete ownership proof.
4. [Network-free runtime control](evidence/RES01_SLEEP_CONTROL.json): the checked-in standalone Swift program imports Foundation only, uses no NetworkKit or network, cancels and joins 6,400 ten-second sleeps, and exposes two snapshot phases. Both clock and nanosecond APIs show 6,403 Task-stack nodes immediately after joined cancellation and two after twelve seconds. Live malloc bytes fall from 3,992,208 to approximately 101,600. This independently reproduces expiry-dependent retention without the library's operation, delegate, session or response ownership.
5. [Post-budget native results](evidence/RES01_POST_BUDGET.json) repeat the original public-client/direct-control workload with a twelve-second post-shutdown sample. These unprofiled results retain request/payload assertions, exact environment/harness hashes and all three repetitions. RSS is interpreted alongside the allocation evidence, not as live-object count. The tracked-checkout flag is false because the candidate measurement scripts/docs were being developed; production Swift source and Package.swift are unchanged from the recorded baseline.

The heap snapshots are not simultaneous: inspection takes time while timers continue expiring. Do not equate a count in a memory graph captured later with an earlier heap count. Small remaining Task-stack counts include the control program and runtime work; they do not mean active library requests remain. The probe's own latency/sample arrays, the client object and framework/allocator caches also remain in scope. Neither leaks-tool output nor a low final RSS is used to assert absence of all leaks.

## Longer observation across timeout windows

A further [64,000-call control](evidence/RES01_LONG_WINDOW.json) runs 1,000 cycles of 64 calls in each of two fresh processes, one repetition per mode. NetworkKit workload duration is 33.89 seconds and the direct control 31.85 seconds, exceeding the ten-second selected budget window several times. Every expected payload/count assertion passed. This supplements the three-repetition shorter measurements; it is not a statistical claim of a universal steady state.

| Process RSS, MiB | Cycle 1 | Cycle 100 | Cycle 200 | Cycle 500 | Cycle 1,000 | Twelve seconds after shutdown |
| --- | --- | --- | --- | --- | --- | --- |
| NetworkKit | 8.27 | 14.59 | 18.93 | 24.40 | 25.08 | 24.06 |
| Direct URLSession | 7.09 | 9.27 | 9.64 | 10.13 | 10.72 | 10.46 |

Growth slows in the later NetworkKit cycles; the final observed RSS is still higher than the direct control. Peak RSS is 26.60 MiB versus 10.81 MiB. This is a finite, ten-second-budget synthetic workload with framework/harness overhead, not a permanent memory bound or proof that all resident-page ownership is explained. The selected production default is sixty seconds; do not extrapolate a target-device allowance from this ten-second diagnostic. Preserve actual rate/budget/platform assessment at the release gate.

## Reproduction

- `python3 scripts/benchmarks/sleep_retention.py --output /private/tmp/networkkit-sleep-retention.json` compiles the network-free Swift control with optimization, Swift 6 and warnings as errors. It launches only owned child processes, snapshots with /usr/bin/heap at both explicit phases, and exports counts/environment/source hashes. Phase waits, profiler commands and teardown are bounded. Raw logs are temporary and no memory addresses, payloads or private keys are published. Profiler errors fail the run; no silent skip. Changed runtimes may eliminate the retention, so counts are observations rather than fixed pass thresholds.
- `python3 scripts/benchmarks/run.py --post-budget --output /private/tmp/networkkit-post-budget.json` builds the public consumer and runs only long reuse/direct cases, three repetitions each, with the twelve-second sample. Default/full and --smoke workloads retain their original short sample; --smoke and --post-budget are mutually exclusive. This mode uses no profiler or extra SDK dependency. Add `--cycles 1000 --repetitions 1` for the longer control; cycle counts are bounded to 1–1,000 and valid only with --post-budget. Per-process timeout is 45 seconds normally or 120 for more than 100 cycles.
- For native ownership inspection, use an isolated copy of Probe.swift: replace its short settled-sample wait with an explicit stdout readiness marker and a 25-second wait. Run the 32 / 65536 / 64 / 100 workload with MallocStackLogging=1 against the existing Fixture from run.py, inspect only that owned PID with `heap -s` after readiness and again after eleven seconds, and save a graph locally using `leaks --noContent --outputGraph=... PID`. `malloc_history GRAPH -callTree -noContent` identifies allocation paths. The recorded summary states the exact probe-only change and the separate direct-control repetition. Do not commit private/raw graphs or compare profiled timing to unprofiled throughput.

CI keeps the normal public release smoke and adds Swift type-checking of the standalone sleep control. Heap inspection remains opt-in: CI does not claim profiler permissions, target-device profiling or a memory-leak gate. A later runtime behavior change is a reason to refresh evidence, not fail a volatile allocation-count threshold.

## Resource limits and remaining acceptance

Concurrency alone does not bound these transient helper allocations: a rapid sequence of short calls can complete while many original timeout instants are still ahead. Consider call rate, payload/retained-result size and selected total budget together. Avoid unnecessarily large timeout overrides. The measured ten-second sleep window is not a hard memory ceiling or a universal retention-duration guarantee; runtime scheduling and allocator caches differ. Production defaults remain 30-second inactivity / 60-second total; this investigation does not shorten them to improve a chart.

Keep the I20 provisional app-evaluation boundary (eight active calls, expected responses up to 1 MiB) as workload guidance only. It is not an SDK response-size/rate limiter, safe bound against hostile bodies, or validated watchOS/device memory allowance. Process RSS can stay high after live allocations disappear. Obtain actual target-device evidence before deciding whether this behavior fits an app's memory/rate/budget requirements.

#62/#63 must record representative target resource behavior, cancellation/shutdown, rate/budget context and observation after original deadlines, using a compatible native profiling/harness route. The macOS-only inspector is not an executable watchOS/iOS/tvOS test. #86/#29 require explicit owner accept/reject/mitigation of this runtime-retention risk and final resource/platform evidence; none is inferred here. If a target remains unsuitable, stop release acceptance and define a bounded corrective design rather than silently changing support, timeouts or cancellation semantics. No residual risk is waived by review completion.
